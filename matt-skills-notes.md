# Matt Pocock's skills: ideas for our SDLC

Working notes while we go through [mattpocock/skills](https://github.com/mattpocock/skills). When we finish, the good ideas move into [our-sdlc.md](our-sdlc.md). Nothing here is agreed yet.

**Skills read so far:** README (all four "Why" sections), `ask-matt`, `grill-with-docs` (with `grilling`, `domain-modeling`, and the glossary and ADR formats), `triage` (with `AGENT-BRIEF.md` and `OUT-OF-SCOPE.md`), `improve-codebase-architecture`, `setup-matt-pocock-skills`, `to-spec`, `to-tickets`, `implement`, `implement-spec`, `wayfinder`, `retro`, `prototype`, `diagnosing-bugs`, `research`, `tdd`, `codebase-design`, `code-review`, `pr`, `wizard`, `grill-me`, `handoff`, `teach` (skimmed), `to-questionnaire`, `wait-what`, `writing-for-agents`, and `PHASE-BOUNDARIES.md`. That is every skill in the README's Reference list.

## What Matt's flow looks like

Idea, grill, (prototype), spec, tickets, implement with `/tdd`, `/code-review`, PR, `/retro`. It maps well onto our intake, spec, plan, build and PR. The big difference: his flow has no Jira. His tickets live in the issue tracker he picks (GitHub, Linear or local files).

Skills are plain `SKILL.md` folders. We could copy them into `.github/skills/`, but we haven't tested that they trigger in Copilot CLI.

## Ideas worth taking

| Idea | Where it fits in our flow | Notes |
|---|---|---|
| **Grilling interview** | Step 1 (intake), maybe step 2 (spec) | The agent asks the **engineer** numbered questions in rounds, each with a recommended answer. It looks up facts itself and only asks for decisions. Today we only send open questions to the product owner. |
| **Glossary (`GLOSSARY.md`)** | Part 2, next to `AGENTS.md` | One short file of project terms, each with an `_Avoid_` list. Shorter, clearer intents and specs, fewer tokens, consistent names. Big repos use a `GLOSSARY-MAP.md` with one glossary per area. |
| **ADRs (`docs/adr/`)** | Part 2 | A short note for decisions that last longer than a ticket. Write one only if it is hard to reverse, surprising without context, and a real trade-off. Our spec's "what we will not do" stays per ticket. |
| **Module question** | Step 2 or 3 | Ask which modules the change touches before writing the spec. We have no design check today. (Correction: the README says `/to-spec` does this, but the skill file only asks about test seams, not modules.) |
| **Codebase health scan** | Outside the ticket flow | `/improve-codebase-architecture` every few days. Findings become Jira tickets, like our step 7. Good for old repos. Read-only: it writes an HTML report to the temp folder, nothing in the repo. It looks first at files that changed recently (git history). It uses the glossary and respects ADRs. |
| **`/tdd` for every feature** | Step 4 (build) | We only require a failing test first for bugs. The skill is a reference, not a recipe. **What we'd take:** (1) test only at the seams agreed in the spec. (2) One test, then just enough code to pass it, then the next test. Not all tests first. (3) Tests check behavior through the public interface, never private methods or the database directly. (4) No tautological tests, where the expected value is computed the same way the code does. Use a known literal. (5) Mock only at system edges (external APIs, time, sometimes the database), never our own modules. (6) Refactoring happens in review, not inside the test loop. These six lines could go into our build instructions as they are. |
| **`/diagnosing-bugs`** | Step 7, and every bug ticket | Six gated phases: build a feedback loop, reproduce and shrink, 3 to 5 ranked hypotheses, instrument, fix with a regression test, clean up. **The key rule:** no theories until there is one command, already run, that goes red on this exact bug, fast and the same every run. It lists ten ways to build one (failing test, curl script, browser script, replaying a captured request, `git bisect`, and so on). **What we'd take:** (1) for every bug ticket, the agent first shows that one red command, then fixes. This sharpens our "failing test first" rule. (2) Show the ranked hypotheses to the engineer before testing them. (3) Tag debug logs with a unique prefix so cleanup is one grep. (4) Redact secrets in everything it shows. (5) Put the real cause in the commit or PR message. (6) If no good place exists for a regression test, that is a finding for the architecture scan. |
| **`/retro`** | After step 4 or 5 | The agent reads the session and suggests changes to the **setup, not the code**, most severe first. It proposes only, and changes nothing. Seven areas: navigation (pointers to files it searched for), automated checks, coding standards, a bloated `AGENTS.md`, expensive tool calls, instructions that change nothing, and missing information (for example dev server logs). **What we'd take:** (1) it would feed our rule "same mistake twice, update `AGENTS.md`", with a regular prompt instead of waiting for someone to notice. (2) **Mechanical mistakes become automated checks** (linter rule, hook, CI job), and only judgement calls become written standards. This matches our hooks idea. (3) Keep `AGENTS.md` tiny, only pointers to other files, and put rules for reviewers in a separate standards file. The reviewer gets only a diff, so it is the right place to enforce standards, and the implementer has the most to think about. (4) Check whether a repo has no guardrail at all (no hook, no CI lint). Also a good first prompt for old repos. |
| **Two-axis review** | Step 5 (AI self-review) | `/code-review` reviews the diff since a fixed point with two parallel subagents. **Standards:** the repo's written standards plus 12 classic code smells (unclear names, duplicated code, speculative extras and so on), always as judgement calls, and the repo's own rules win. **Spec:** what is missing, what was built but not asked for, and what looks wrong, each quoting the spec line. The two reports stay separate and are not merged or reranked, so one can't hide the other. **What we'd take:** this is a good shape for our agreed review prompt in Part 2. The spec check fits us well, because our PR carries the intent, spec and plan. The "built but not asked for" check uses our spec's "what we will not do". |
| **`/pr` body shape** | Step 5 | A PR body template: **Summary** as the smallest visual that makes the point (pseudocode, call tree, file tree, Mermaid, or a small diff), **Evidence** before and after (screenshots best, then test output), and **Merge danger**: one-way or two-way door (can we roll it back?) plus blast radius. **What we'd take:** the template as is for the PR the build session opens. Merge danger also helps our release step decide how careful to be. |
| **Agent brief** | Step 3 (plan), and for tickets handed to an agent | A durable contract: current and desired behavior, key interfaces, testable acceptance criteria, and out of scope. No file paths or line numbers, because they go stale. Compare with our plan's "Done when". |
| **Verify before building** | Step 1 (intake) | For a bug, the agent reproduces it from the ticket's steps first. A reproduced bug makes a much stronger plan. "Not enough detail to reproduce" is a signal to ask the reporter. |
| **Redundancy check** | Step 1 (intake) | Before building, the agent searches the code for the requested behavior, by concept and not by wording. Saves building something that already exists. |
| **Out-of-scope notes (`.out-of-scope/`)** | Part 2 | One short file per rejected concept, with the reason and the tickets that asked for it. Checked at intake so we don't re-argue old decisions. Only for rejected features, not for ones already built. |
| **AI disclaimer on posts** | Steps 1 and 6 | Every Jira comment the agent writes starts with "This was generated by AI". Fits how we already post questions and release summaries. |
| **Per-repo setup skill** | Part 2 | Run once per repo. It asks (issue tracker, labels, docs layout), shows a draft, then writes small files in `docs/agents/` and adds a short "Agent skills" block to `CLAUDE.md` or `AGENTS.md`. Jira would be the "other" tracker, described in one paragraph. We could write one setup skill for our own flow. It does not create `GLOSSARY.md`. |
| **Spec template and test seams** | Step 2 (spec) | `/to-spec` writes the spec from the chat with no new interview. Template: problem, solution, user stories (a long list), implementation decisions, testing decisions, out of scope, notes. No file paths or code, because they go stale. It first agrees the **test seams** with the engineer: the fewest, highest points to test from, ideally one. Our spec has no user stories or testing section today. **What we'd take:** (1) a short "Testing" section in our spec: what behavior we test from the outside, at which points, and which existing tests to copy. For BILL-123: one integration test through `GET /invoices/export`, like the existing endpoint tests. (2) 3 to 6 short user stories for the product owner to confirm, not Matt's "extremely extensive" list. **What we'd skip:** publishing to an issue tracker (ours stays a Markdown file linked from Jira), no-interview mode (grilling happens first, in step 1), and file paths (they stay in the plan). |
| **Vertical slices with blockers** | Step 3 (plan) | `/to-tickets` splits work into "tracer bullet" slices: each goes through every layer (schema, API, UI, tests), can be verified alone, fits one fresh session, and lists which slices block it. **What we'd take, inside the plan file:** (1) a slice rule: each task verifiable alone and sized for one session. For BILL-123: one thin slice first (basic CSV download from endpoint to button), then one for the 10,000-row limit and logging. (2) A "Blocked by" line per task, so the main session knows what it can hand to parallel subagents now. (3) Prefactor first: if the code is awkward, the first task makes it easy with no behavior change. **Catch:** slices through every layer touch the same files, so they can't run in parallel worktrees. Use slices for work done in order, and layer tasks (different files) when we want parallel subagents. **What we'd skip:** separate tickets per slice (one ticket, one plan, one PR), and expand-contract for big renames (rare for us, add later if needed). |
| **Build loop from `/implement`** | Step 4 (build) | A tiny skill (5 lines): build the work with `/tdd` at the agreed test seams, run type checks and single test files often, run the full suite once at the end, then `/code-review`, then commit to the current branch. **What we'd take:** the cheap-to-expensive order for checks (type check and one test file while building, full suite once at the end), which saves time and tokens per subagent. The seams come from the spec's Testing section. We already have the rest (full suite at the end, review, commit). |
| **Parallel build with subagents** | Step 4 (build) | `/implement-spec` builds a whole spec on one integration branch. The tickets form a task graph, and the agent keeps starting **implementer subagents** (each in its own worktree, each using `/tdd`) for every ticket whose blockers are done, running in the background. Separate **merger subagents** merge each result into the integration branch. Last, one `/code-review` over the whole branch, one subagent fixes the findings, and the worktrees are cleaned up. **What we'd take:** (1) start the next tasks as soon as their blockers finish, instead of fixed rounds. (2) A separate merger subagent, so the main session stays clean. (3) Subagents get **pointers** (plan, spec, notes, earlier commits), not copied text. (4) Each subagent merges the branch tip into its own branch before reporting done, so conflicts show early. (5) An exploration subagent saves notes outside the repo for all later subagents. (6) A worktree cleanup step at the end. **Already like ours:** worktree per subagent, one integration branch, one review at the end. **Warnings from his docs (`docs/engineering/implement-spec.md`):** (a) a worktree holds only what git tracks, so tests that need gitignored fixtures, local databases or credentials can silently skip and report green. Run those in the main checkout. (b) The orchestrator should track which tasks are merged itself, because a tracker's blocked-by count only drops when a ticket closes. (c) Run `/code-review` only once, at the end, not per ticket. **Unattended work:** he has no "Ralph loop". He says AFK (away from keyboard) and uses a plain loop (his [Sandcastle](https://github.com/mattpocock/sandcastle), a shell script or a CI job). For truly unattended work this is faster, cheaper and more reliable than an agent orchestrating, because no agent makes the orchestration decisions. `/implement-spec` is for when you want to watch and steer. |
| **Map for big, foggy work (`/wayfinder`)** | Before step 1, for epics only | For an idea too big for one session. One "map" issue holds the destination, notes, decisions so far, "not yet specified" fog, and out of scope. Child tickets are **decisions, not build tasks**, one per session. Types: research (agent alone), prototype and grilling (with a human), task (manual work that unblocks a decision). Rule: don't chart what you can't see yet. Fog becomes tickets only when the frontier reaches it. When the map clears, it hands off to `/to-spec`. **What we'd take (later, only if we get epics):** (1) a one-page epic map in Jira with decisions so far, open questions and out of scope. (2) "Decisions, not deliverables" for the early phase of a big feature. (3) A not-yet-specified list so we don't ticket too early. **What we'd skip for now:** the full skill. Our tickets come from the product team already sized for one flow. |
| **`/ask-matt` router** | Onboarding | A skill that points a new teammate to the right step. We would write our own for our flow. |
| **`/wait-what`** | Any step | Three lines: re-explain the last message with a bit of context, in Simplified Technical English, using the glossary's words. Easy to copy as our own one-line skill. |
| **Deep modules vocabulary (`/codebase-design`)** | Step 3 (plan), review | Shared words for design: module, interface, depth, seam, adapter. Rules: a deep module has a lot of behavior behind a small interface. The deletion test asks whether deleting a module would move its complexity to every caller (worth keeping) or make it disappear (a pass-through). The interface is the test surface. Add a seam only when two real versions exist. **What we'd take:** these few words in our plan step for the "where does it belong" question, so plans and reviews talk the same way. |
| **Prototype** | Steps 1 to 3, when a question can't be settled on paper | Throwaway code that answers one question. For logic, a single HTML file that walks a state machine through hard cases, which a non-developer can click through. For UI, several very different designs on one page, switched by a URL parameter. No tests, no persistence. Keep it on a throwaway branch and write down the answer. **What we'd take:** a UI prototype lets the product owner pick a design before the spec is final. |
| **Research in the background (`/research`)** | Steps 1 to 3 | A background agent reads primary sources (official docs, source code) and writes one Markdown file with a source for each claim. You keep working. **What we'd take:** for a question about a third-party API, a research file linked from the intent or spec. |
| **`/handoff`** | Between sessions, only when needed | Writes a handoff file to the temp folder, with pointers to the spec, plan and commits instead of copies, suggested skills for the next agent, and secrets removed. **For us:** our committed intent, spec and plan already do this. Use it only for a side task, a colleague, or a switch to another tool. |
| **Questionnaire for one person (`/to-questionnaire`)** | Step 1 (questions to the product owner), step 6 (release questions) | It asks you only who the questions go to and what you need back. Then it writes a Markdown questionnaire, most important first, one idea per question, with a short "why this matters" where needed and a closing "anything else?". **What we'd take:** the shape for the open questions we send the product owner or the security team, instead of a loose Jira comment. |
| **Bash wizard for manual steps (`/wizard`)** | Part 2 setup, step 6 | A bash script that walks a human through steps only they can do (create credentials, set CI secrets, a one-off migration). It opens each URL, captures values, writes `.env` and GitHub secrets, and asks to confirm before anything that can't be undone. **What we'd take:** for repo setup (secrets, AWS role) and one-off cutovers. Commit it if the setup repeats. |
| **Writing rules for agent files (`/writing-for-agents`)** | Part 2 (`AGENTS.md`, skills) | How to write files an agent reads. Each line in an always-loaded file costs tokens on every turn, so keep it short and put details in other files behind a clear pointer. Each step needs a clear "done when". Say what to do, not what not to do, because a ban puts the idea in the agent's head. Delete lines that change nothing, and don't copy facts the agent can look up (scripts, config). Prefer one strong word ("tight", "red") over a sentence. **What we'd take:** these rules as our checklist for `AGENTS.md` and every skill we write. |

## Context rules from `ask-matt`

- Keep grilling, spec and tickets in one unbroken session. Start each build session fresh from the ticket.
- Stay in the "smart zone", about 150k tokens. Past that, the model reasons worse.
- At a phase boundary the order is: continue, `/clear`, `/handoff` (only for a new tool, folder or person), subagent, `/compact` (the default).
- Compare with our "one session per step" rule. Same idea, a little different.
- `PHASE-BOUNDARIES.md` explains why. **Continue** keeps the session as a primary source. Every other move replaces it with a summary, which loses detail. So continue when the next phase needs this one's reasoning (grilling into building is the standard case) and there is room left. `/clear` when nothing in the session matters any more. Clearing a session that did matter loses the "why" for good. Use a subagent for work that needs no steering, such as an automated review. `/compact` with an instruction ("we're going to QA this area") is the last choice.
- **Possible change for us:** our rule starts a new session for every step. Matt would keep intake (grilling) and spec in one session, because the spec needs the interview's reasoning. Worth discussing. Our committed files reduce the loss, but they don't hold everything.
- Decide this at a phase boundary only. Mid-phase, either continue or split the rest into subagents.

## What we would not take

- The `/triage` state machine (labels such as `needs-triage` and `ready-for-agent`) and the full `/wayfinder` skill. Our product team and Jira already sort the tickets, and our tickets are not too big for one flow. We only take the single ideas from `/triage` listed in the table.
- Tickets and specs published to an issue tracker. Jira stays our source of truth.
- `/grill-me` (`/grill-with-docs` without saving anything). We always work in a repo, so `/grill-with-docs` is the one to use.
- `/teach`. A skill for learning a topic over several sessions with lessons and records. Useful for the training, not for the SDLC.

## Open questions

- Who owns the glossary in each repo? The agent writes the entries in a grilling session, but a human must confirm them. I'd propose the engineer in the session, and code owners in the PR.
- Who writes `GLOSSARY-MAP.md`? Neither `grill-with-docs` nor the setup skill creates it (setup only offers a multi-context layout for monorepos).
- Do the skills load properly in Copilot CLI?
- Is a glossary worth it for repos with a single small area?
- Where would an agent brief live for us: in the plan file, or as a Jira comment?
- Where would `.out-of-scope/` live: in each repo, or in one shared place?
- Does the grilling replace the intent template, or work before it?
- Should intake and spec share one session, as Matt suggests, or stay separate as in our flow today?
- Do we need a `CODING_STANDARDS.md` per repo for the review, kept apart from `AGENTS.md`?

## Decisions so far (for our-sdlc.md)

**Step 1, intake**
- Grilling round: yes, for every feature. It runs after the agent reads the ticket and before it writes the intent. Small bugs and chores skip it, like the intent.
- "Already exists?" check: yes. The agent searches the code for the requested behavior and reports where it looked.
- Bug reproduction: try, don't block. A failing test locally if possible, else in the dev env, else confirm the symptom from prod logs (read-only). If none works, write "not reproduced" in the intent and carry on. The failing test is then built in step 4.
- Questions to the product owner: questionnaire shape in the Jira comment. Most important first, one idea per question, each with a default, and a short "why this matters" where needed.
- "Generated by AI" line on Jira comments: no.

**Step 2, spec**
- Testing section: yes (which behavior we test, at which points, which existing tests to copy).
- User stories: no. The product owner won't read the spec. Devs write it.
- Do we need a spec at all? Open. Maybe only for big tasks. (See follow-up below.)
- Prototype: yes, optional. The engineer decides. Kept on a throwaway branch, and the answer goes into the spec or plan.
- Intake and spec in one session: yes, so the spec keeps the grilling's reasoning. The intent is still committed first.
- Follow-up (not answered yet): my suggestion is no separate spec by default. The plan file starts with a short "What we build" part (decisions, what we will not do, Testing), then "How and where". A separate spec only for big tasks (several services, a security or privacy review, more than a few days). The product owner confirms only the intent, in Jira. Open: who decides a task is "big", the engineer or a fixed rule?

**Step 3, plan**
- Task split: the engineer picks per ticket. Thin end-to-end slices when tasks run one after another. Split by layer when we want parallel subagents (different files).
- Every task has a "Blocked by" line ("Blocked by: A" or "nothing") and fits one session. Too big means split it.
- Prefactor task first when the code is awkward: no behavior change, tests stay green.
- Shared design words: yes, a short list (module, interface, seam, deep vs shallow) with one-line meanings, in `AGENTS.md` or a linked doc.

**Step 4, build** (test rules and parallel ideas picked by Claude on request)
- Test rules: (1) test only at the points agreed in the Testing section, (2) one failing test, then just enough code to pass, then the next, (3) test behavior through the public interface, never internals, (4) expected values are known literals, never recomputed like the code, (5) mock only external systems (external APIs, time, sometimes the database), never our own modules.
- Not taken: "refactor in review". Our AI review is optional, so cleanup could be skipped. The agent tidies up inside the build, before the engineer reviews the diff.
- Bug tickets: the agent first shows one command that fails on this exact bug. Try, don't block: a failing test locally, else a script against the dev env. If impossible, say so and fix from logs. The real cause goes in the PR.
- Parallel build: (1) start a task as soon as its blockers finish, (2) subagents get pointers to the intent, spec, plan and commits, not pasted text, (3) each subagent merges the latest feature branch into its own before reporting done, (4) remove the task worktrees at the end. Warning: tests that need untracked files (fixtures, local DB, secrets) can silently skip in a worktree, so run those in the main checkout.
- Not taken: a separate merger subagent. The main session keeps merging, as today.
- Check order: type check and the one test file while building. Full build, test and lint once at the end, on the merged result.

**Step 5, PR**
- AI self-review: two separate reports. Standards (our written rules plus common code smells, as judgement calls). Spec (missing, built but not asked for, looks wrong, each quoting the spec or plan line). Not merged or reranked.
- PR body: Matt's template. Summary as a small visual, evidence before and after, merge danger (can we roll it back, and what could it affect).
- `CODING_STANDARDS.md` per repo: yes, later. Read only by the reviewer, so `AGENTS.md` stays short. Starts empty and grows when the same review finding shows up twice. It replaces the `REVIEW.md` idea in Part 2.
- Retro: when something went wrong. The agent proposes setup changes. Mechanical mistakes become a check (lint rule, hook, CI), judgement calls go to the standards file. The engineer picks what to apply.

**Spec follow-up**
- No separate spec by default. The plan file starts with "What we build" (decisions, what we will not do, Testing). A separate spec only for big tasks. The engineer decides, with a guide: spans several services, needs a security or privacy review, or takes more than a few days. They can ask a tech lead.

**Part 2, setup**
- `GLOSSARY.md` per repo: grows from intake grilling. The engineer confirms terms in the session, code owners review in the PR.
- ADRs in `docs/adr/`: yes. `.out-of-scope/`: no.
- `AGENTS.md`: short rules and pointers only, written with the writing-for-agents rules.
- Architecture scan: monthly, read-only report per repo. A tech lead picks candidates, which become Jira tickets.
- Own skills, later (picked by Claude on request): setup skill, router skill ("ask our SDLC"), bug diagnosis skill. Not wait-what (a one-line prompt is enough).

**Steps 6 and 7** (picked by Claude on request)
- Release reads the PR's merge-danger line. A one-way door gets a longer log check and a named approver.
- Step 7 production findings use the bug process: one failing command, ranked causes, then the fix.
- Bash wizard: optional, for manual setup a human must do (AWS role, CI secrets).

**Apply:** all at once into `our-sdlc.md`, no commit until the user says.
