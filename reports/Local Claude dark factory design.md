# Run sdlc-ticket unattended on your Mac

Build the first version as **a small local program that runs your `sdlc-ticket` skill unattended**. It is not a new agent system. The setup is one Python process on your Mac. It polls Jira with your own token and makes a worktree per ticket. It starts one headless Claude Code session per ticket with the Claude Agent SDK (or `claude -p`), saves everything in **one SQLite file**, and serves a local dashboard whose top section is "needs you". You do not need LangGraph or any other agent framework. Your skill already is the workflow graph, and Claude Code already gives you session resume, a `defer` hook for pausing at a question, per-model cost, and budget and turn caps. The evidence on databases also differs from what you expected. **Most local, single-user orchestrators use SQLite**: 9 of the 16 open-source projects checked, and most local tools in your own wiki. The well-known Postgres examples (Cole Medin's Factory Mission Control and Agent Control Plane, on hosted Neon) chose Postgres for hosted features that a local factory does not need. A run goes from intake to a draft PR with no plan gate, just like `sdlc-ticket`. It never merges or releases, and it posts nothing to Jira or GitHub except the draft PR. The hard parts are not the AI. They are pausing for expired AWS credentials, keeping your personal tokens fenced, and making every step safe to repeat.

## What changed from the earlier report

The earlier report planned for a Copilot runtime, admin help and a later move to containers. The new constraints remove all three. This table lists what was dropped or changed.

| Earlier recommendation | Now |
|---|---|
| Runtime-neutral core, prove `copilot -p` first | Claude only. Keep a small "runner" function so a Copilot path can come back later, but don't build an adapter now |
| Phase 2 plan approval gate in the dashboard | Dropped. A run goes on to the draft PR, as `sdlc-ticket` does |
| Phase 1: no push, no PR | Push and draft PR are on in phase 1 when the repo's policy says yes, because that is what `sdlc-ticket` does |
| Jira service account, GitHub App token, AWS role by OIDC, "ask security", ask for Rovo or Copilot for Jira | Dropped for now. Only your personal Jira token and your `gh` login |
| Push intake (Automation → `workflow_dispatch`) | Dropped. Polling only |
| Ephemeral containers, GitHub Actions runner, self-hosted Langfuse or Grafana | Not in early phases. Everything runs on the Mac, with the macOS sandbox instead of containers |
| Reviewer on another model family (GPT-6.1 Sol in Copilot) | Claude only: Opus reviews code that Sonnet wrote, in a fresh context |

The rest still holds: an opt-in JQL poll, a lock per ticket, SQLite with an append-only events table, an attention-first dashboard, pinned models, hard caps, and treating ticket text as untrusted.

## Claude Code is the harness; your skill is the graph

Every coding-agent factory checked runs **the vendor's harness inside a thin, deterministic orchestrator**. None of them uses a general agent framework. Vibe Kanban starts the Claude CLI with `--output-format=stream-json` in each worktree ([vibe-kanban](https://github.com/BloopAI/vibe-kanban)). Archon's Claude provider is the Claude Agent SDK ([Archon](https://github.com/coleam00/Archon)). OpenAI's Symphony polls the tracker, makes a workspace and runs Codex in app-server mode ([Symphony](https://github.com/openai/symphony)). LangChain itself puts the Claude Agent SDK in a separate "agent harness" category, apart from frameworks (wiki: `wiki/sources/langchain.com-deepagents.md`). Anthropic's advice is to start simple, because frameworks "make it tempting to add complexity when a simpler setup would suffice" ([Building effective agents](https://www.anthropic.com/research/building-effective-agents)).

The reason is practical. LangGraph, Mastra, CrewAI and the others would each run their own loop on the raw model API. You would lose Claude Code's tools, skills, subagents, hooks, CLAUDE.md and permissions, or you would wrap Claude as one opaque node. Your intake → plan → build → review → PR → verify chain already lives in `sdlc-ticket`. Rebuilding it as a graph would give you two sources of truth. **The SDK loads the same skills, subagents, hooks and CLAUDE.md as the CLI** when `settingSources` is left at its default ([SDK: Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)). Sending `/<name>` in the prompt starts a user-invoked skill ([Skills in the SDK](https://code.claude.com/docs/en/agent-sdk/skills)). So your skills run unchanged.

**`claude -p` and the SDK drive the same binary**, so the choice between them is about convenience ([Headless](https://code.claude.com/docs/en/headless)). Pick the Python SDK. Its `canUseTool` callback and typed result message give you `session_id`, `total_cost_usd`, per-model usage and `stop_reason` without parsing text. Its pluggable session store and fork come free ([User input](https://code.claude.com/docs/en/agent-sdk/user-input); [Cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). Three traps matter. **Never use `--bare`**: it skips skills, subagents and CLAUDE.md, and the docs say it will become the `-p` default in a future release, so set the setting sources explicitly. **From v2.1.302, `-p` starts in Manual mode** and denies anything that needs approval unless you set a mode or a permission host. Without one, build steps fail quietly. **A `-p` run without `--bare` runs the repo's hooks and `.mcp.json` servers** with no trust dialog, so point it only at repos you trust ([Headless](https://code.claude.com/docs/en/headless)).

Use **one session per ticket**, running the whole `sdlc-ticket` chain, exactly as you do today. Its subagents keep the main context small, and its files (intent, plan, Build log markers) let a fresh session continue if one dies. Bring in a durable engine (DBOS on SQLite first, then Temporal) or a framework only when one of these happens: you have several machines, you run many parallel tickets with side effects that must happen exactly once, the stage graph moves out of skills into code, or you mix runtimes. None of the 16 orchestrators checked, and no factory in your wiki, uses Temporal, DBOS, Inngest, Restate or Trigger.dev. If you need one later, Temporal's dev server runs locally on a SQLite file ([Temporal CLI](https://docs.temporal.io/cli/command-reference/server)).

## SQLite is what local tools use; Postgres arrives with hosted features

Here is what the evidence shows, plainly. **In a direct check of 16 open-source agent orchestrators, 9 store their state in SQLite.** They are Vibe Kanban, Crystal, Sculptor, Archon (its default), Claude Code UI, opcode, Ralph's web server, Agent Orchestrator and builderz-labs' Mission Control. Only Paperclip and Langfuse need Postgres. Symphony, Claude Squad and HumanLayer's Kubernetes control plane use no SQL database at all ([Archon connection.ts](https://github.com/coleam00/Archon/blob/dev/packages/core/src/db/connection.ts); [Agent Orchestrator db.go](https://github.com/OrchestratorInc/agent-orchestrator/blob/main/backend/internal/storage/sqlite/db.go); [Mission Control db.ts](https://github.com/builderz-labs/mission-control/blob/main/src/lib/db.ts); [Sculptor](https://github.com/imbue-ai/sculptor/blob/main/sculptor/sculptor/database/README.md)). Archon's README calls it a "single-developer tool" on "SQLite/PostgreSQL", and it switches to Postgres only when `DATABASE_URL` is set.

**Your agentic AI wiki shows the same thing.** Local tools there use SQLite (Vibe Kanban, Phasr, Archon's default, Ouroboros's append-only event store) or plain files (ZazenCodes' `job.json`, firstmate, Ralph's JSONL, oh-my-claudecode, Cabinet, evo). Symphony keeps no database by design ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)). You were partly right: the most visible factory dashboards in the wiki do use Postgres. Cole Medin's Factory Mission Control puts "every fact in one Postgres database", and his Agent Control Plane writes `loops`, `runs` and `run_events` to Neon. But both use **hosted Neon** for Neon Realtime live queries, database branches for tests, a 7-day rewind and webhooks through Neon Functions ([Factory Mission Control](https://github.com/coleam00/factory-mission-control); [Agent Control Plane](https://github.com/coleam00/agent-control-plane)). A local-only factory can't use those features. Paperclip, the other Postgres case, embeds Postgres so that nobody has to run a server ([Paperclip](https://github.com/paperclipai/paperclip)). Watch out for two name clashes: builderz-labs' "Mission Control" runs on SQLite, and HumanLayer's "agentcontrolplane" is a Kubernetes project, not Cole's.

The local projects also settled on the same SQLite settings. Archon, Agent Orchestrator, Mission Control and Ralph all use **WAL, `busy_timeout=5000`, `synchronous=NORMAL` and `foreign_keys=ON`**. Archon sets the busy timeout *before* WAL, because two processes can contend on switching WAL on. Sculptor moved to WAL after "DB-locking errors seen under concurrent access" ([Archon sqlite.ts](https://github.com/coleam00/Archon/blob/dev/packages/core/src/db/adapters/sqlite.ts); [Sculptor core.py](https://github.com/imbue-ai/sculptor/blob/main/sculptor/sculptor/database/core.py)). Plain JSON files are fine for append-only logs, but they have no transactions and are hard to query for a dashboard. Symphony shows the cost of keeping no database: its "waiting for approval" entries live only in memory, and a restart clears them ([Symphony README](https://github.com/openai/symphony/blob/main/elixir/README.md)). Your factory pauses for you, so it has to persist that state.

So use **one SQLite file at `~/.factory/factory.db`**, opened with Python's built-in `sqlite3`, and keep a migrations folder from day one. One rule matters most: **only the factory process writes to the database**. Agents and hooks report through it. Keep big transcripts as files and store only their paths. Close connections explicitly. Cole's factory hit file-lock errors because the `sqlite3` context manager commits but does not close ([ai-software-factory](https://github.com/coleam00/ai-software-factory)). Keep a `DATABASE_URL` seam in case a team server comes later.

**Supabase gets used in agent tools, but not as the main store of a local factory.** The best-known case moved away from it. Archon v1, the old Python version, ran only on Supabase Postgres. The current Archon is "SQLite by default, PostgreSQL if you want it" ([Archon v1](https://github.com/coleam00/Archon/tree/archive/v1-task-management-rag); [Archon README](https://github.com/coleam00/Archon)). Elsewhere, Supabase handles login and cloud sync in Phasr, which keeps its work state in SQLite, and the large shared setup in GBrain, whose default is embedded PGLite. Small projects (0–30 stars) such as agent-hub, agent-team-monitor and metarelay use hosted Supabase as a **cloud relay**: Claude runs locally, and Supabase Realtime, Auth and a queue table feed a phone or web dashboard ([agent-hub](https://github.com/nachoeguillor/agent-hub); [agent-team-monitor](https://github.com/rezaan6/agent-team-monitor); [metarelay](https://github.com/dsifry/metarelay)). You need that pattern only when the dashboard lives off the machine. Running it locally with `supabase start` is now lighter: about **290 MiB idle and a 360–550 MB download** since CLI v2.119. It still means about 13 services, plus Docker or OrbStack, or an experimental native runtime for Apple silicon with no compatibility promise ([Supabase blog](https://supabase.com/blog/local-supabase-project-per-agent-with-or-without-docker); [runtimes](https://supabase.com/docs/guides/local-development/docker-and-native-runtimes)). Its real extras are Realtime for the live dashboard and pgmq queues ([Queues](https://supabase.com/docs/guides/queues)). At this scale, SSE and a leased-jobs table give you the same thing with no extra services. So stay on SQLite, write Postgres-compatible SQL behind the seam, and keep hosted Supabase as **one later team path**. Supabase has a Sydney region (`ap-southeast-2`) that holds the database, Auth, Storage and backups. But logs are stored in EU data centres, support works worldwide, and the primary processor is Supabase Pte. Ltd. in Singapore ([regions](https://supabase.com/docs/guides/platform/regions); [data residency FAQ](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq)). A fintech risk team has to clear that, especially because transcripts can hold secrets or customer data. Self-hosting Supabase or running plain Postgres in the company's own AWS Sydney account avoids those questions. Also note that free hosted projects pause after about 7 idle days.

## One local process runs the poller, the runs and the dashboard

```
launchd (keeps it alive)
  └─ factory (one Python process, 127.0.0.1 only)
       ├─ poller: every 3 min, Jira REST + JQL with your token → upsert tickets
       ├─ scheduler: lock per key, max 1 run (later 2-3), re-check ticket before start
       ├─ runner: worktree.sh → Agent SDK query("/sdlc-ticket KEY factory")
       │          cwd = worktree, settingSources user+project, caps, sandbox
       │          stream events → events table + runs/<id>/stream.ndjson
       ├─ decisions: end-report items, stops and deferred questions → inbox
       ├─ dashboard: FastAPI + HTMX pages, SSE live feed, POST for answers
       └─ SQLite ~/.factory/factory.db (WAL)
  Claude Code transcripts stay in ~/.claude/projects/*.jsonl
  Worknotes (intent, plan, checks, Build log) stay in your private worknotes repo
```

Use four tables. **`tickets`** holds the key, repo, summary, Jira status and updated time, and the factory stage. **`runs`** holds one row per session or resume: `session_id`, worktree, branch, model, status (`queued`, `running`, `waiting_human`, `done`, `failed`, `parked`), `stop_reason`, cost, turns, PR URL and transcript path. **`decisions`** holds the question, options, safe default, deadline, answer, and who answered and when. **`events`** is an append-only log that feeds the live feed. The wiki shows the same "event log plus current state" pattern again and again: Agent Control Plane's `run_events`, Ouroboros's event store and firstmate's status events with a reconciler ([Agent Control Plane](https://github.com/coleam00/agent-control-plane); [Ouroboros](https://github.com/Q00/ouroboros); [firstmate](https://github.com/kunchenguid/firstmate)). The stage can also come from your existing `status.sh`, so the factory reads the same markers the skill writes.

**For the dashboard, use FastAPI + server-rendered HTML with HTMX + SSE.** It is one process with no JavaScript build, which suits one user. Most peers use React + Vite (Vibe Kanban, Archon, Paperclip, Sculptor, Cole's Mission Control). Move to that if the UI grows. A Bun + Hono + React stack in TypeScript is the other good choice if you prefer the TypeScript SDK. Live updates in peers use SSE or WebSocket. SSE fits here: the server pushes, and your answers are plain POSTs ([vibe-kanban events.rs](https://github.com/BloopAI/vibe-kanban/blob/main/crates/server/src/routes/events.rs)). Lay the page out with the **"needs you" queue first**, then tickets by stage, then the live feed. Claude Code's agent view uses the same idea, marking "Needs input" in yellow so you step in "only when a row needs you" ([agent view](https://code.claude.com/docs/en/agent-view#read-session-state)). Each run page links to the Jira ticket, the PR, the transcript and the plan, and shows a `claude --resume <id>` command so you can take over in a terminal.

**Intake uses only what you already have.** `sdlc-setup` already keeps a Jira REST token in a local credentials file. Poll every 2 to 5 minutes with an opt-in JQL such as `assignee = currentUser() AND status = "To Do" AND labels = agent-ready`. Personal API-token traffic falls outside Atlassian's points-based rate limits ([Atlassian rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting)). Treat each hit only as a hint. Re-read the ticket by key, lock it, and check it again right before the run starts and before the push. The factory acts as *you* in Jira, so it can't filter out "its own" edits. That means it must deduplicate from its own database, not from Jira update events. If adding a label is awkward, put a "Start" button on the dashboard next to each assigned ticket. Either way, you still choose what gets built.

## Most pauses come at the end; the rest use resume and defer

`sdlc-ticket` already does most of the hard work for human decisions. It asks once at the start, then "investigates instead of asking", writes down assumptions, and leaves questions, drafts and blockers for the end report. In the factory, **the start round becomes a per-repo policy file** kept in your private worknotes. It covers the base branch rule, the branch pattern, and yes or no for commit and push, draft PR, new mock stubs and lower-env deploy. The skill gets a `factory` note that tells it to read that file instead of asking. It also writes the end report as a small JSON file next to the plan, so the factory reads fields instead of prose. The factory creates the worktree itself and starts the session there, which replaces `/add-dir`.

That leaves three kinds of pause. **End-report items** (questions for the team, notes to send, what blocks the merge) become decisions after the run ends. Nothing gets posted automatically. In phase 1 you copy the approved text and post it yourself, which keeps your rule that nothing goes out before you approve the exact text. **Mid-run stops** (expired AWS credentials, "too big", "already built", a contradicting ticket) end the session with a reason. You fix the cause, for example by refreshing the credentials file in your own terminal with the `pbpaste` command, and click Resume. The factory then runs a new query with `resume=<session_id>` and your answer ([Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)). **Live questions** use the `defer` hook. A `PreToolUse` hook returns `permissionDecision: "defer"` on `AskUserQuestion` or a risky tool. The process exits with `stop_reason: "tool_deferred"` and the pending call. On resume, the same hook returns `allow` with your answer in `updatedInput`. It works only in `-p` and SDK runs, and only when that turn makes a single tool call ([Hooks: defer](https://code.claude.com/docs/en/hooks)). `canUseTool` can wait forever, but that keeps a process alive. Use `defer` for anything that may wait hours ([User input](https://code.claude.com/docs/en/agent-sdk/user-input)). Give every decision a deadline and a safe default: park the ticket and never approve.

## Pin models, cap spend, and fence a run that holds your keys

**Models.** Keep the skill's split. It rests on your DSM-960 trial, where Sonnet broke intake rules on every run and Opus broke none. That means Opus for the main session, intake, plan and review, Sonnet for build and verify, and Haiku for searches. The skill passes aliases (`opus`, `sonnet`, `haiku`), so pin them in the factory's environment with `ANTHROPIC_DEFAULT_OPUS_MODEL=claude-opus-5-5` and the matching Sonnet and Haiku variables. Aliases "update over time" ([Model config](https://code.claude.com/docs/en/model-config)). Also set `--fallback-model`. With Claude only, the reviewer is "another model" because Opus reviews Sonnet's code in a fresh context.

**Cost caps.** Set `max_budget_usd` per run (subagent spend counts toward it) and `max_turns` (unlimited by default). Add your own wall-clock timeout, because a run can go past the cap by one response plus any subagents still running ([CLI reference](https://code.claude.com/docs/en/cli-reference); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Start with about **$20 and 2 hours per ticket**, then tune from real data. Spend restored by `--resume` doesn't count toward the new cap, and the reported total includes earlier runs. So the factory should keep the running total per ticket in `runs` and refuse a resume once the ticket's ceiling is reached. If you run on your Claude subscription, the cost figures are estimates, and Opus "uses up the usage window fast". Factory runs compete with your interactive work, so run them in quiet hours or switch to an API key.

**Logging and tracing.** In phase 1 you don't need a tracing backend. The stream-json events go to a file per run and into the `events` table, and the result message gives cost, per-model usage and turns. Langfuse self-hosted needs Postgres, ClickHouse, Redis and MinIO, which is too much for a laptop ([Langfuse compose](https://github.com/langfuse/langfuse/blob/main/docker-compose.yml)). Set `TRACEPARENT` and `OTEL_RESOURCE_ATTRIBUTES=ticket.id=…,run.id=…` on every run anyway. Claude Code then stamps `trace_id` on its event records even with no exporter, and you can add a local OTel collector later without changes ([Monitoring](https://code.claude.com/docs/en/monitoring-usage)). Keep prompt and output capture off. The transcripts already hold the full content.

**Safety.** The run holds your personal Jira token and your `gh` login, so it can do anything you can. Never use `--dangerously-skip-permissions` on the laptop. The docs reserve it for containers and VMs. Use `dontAsk` mode with an explicit allow list: edits in the worktree, the skill's scripts, git on the ticket branch, `gh pr create --draft`, and the repo's test and lint commands. Add **deny rules, which apply in every mode**, for `gh pr merge`, `gh pr ready`, force pushes, pushes to protected branches, `gh api` writes, and any Jira write ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Turn on the macOS Seatbelt sandbox with `allowUnsandboxedCommands: false`, `failIfUnavailable: true` and a network allowlist (the model API, GitHub, your Jira host, package mirrors). Mask secrets with the sandbox `credentials` setting ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Back the deny rules with a `PreToolUse` guard hook, because hooks still fire where prompts are ignored ([harness-engineering-demo](https://github.com/coleam00/harness-engineering-demo)). Pass ticket text as quoted data. Willison's "lethal trifecta" is private data, untrusted content and a way out, and the egress allowlist removes the way out ([Simon Willison](https://simonwillison.net/2025/Oct/22/living-dangerously-with-claude/)). Bind the dashboard to `127.0.0.1` only. Make every side effect idempotent: fixed branch names, "PR exists?" checked before creating one, and a lock per key.

## A phased plan that starts with one headless run

|---|---|---|---|
| **0. Prove it headless (a few days)** | `sdlc-ticket` finishes with nobody at the keyboard | Run `claude -p "/sdlc-ticket KEY factory" --output-format stream-json --permission-mode dontAsk --allowedTools … --max-budget-usd 20` by hand on a small real ticket. Check that the skill starts, that subagent models are honoured, that no prompt gets denied, and that a gap sent back with `SendMessage` reaches the same subagent (the docs say it should, see below). Set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` so a long subagent isn't cut off at 10 minutes. Add the `factory` mode to the skill (policy file instead of the start round, JSON end report) | Three tickets reach a draft PR and an end report with no prompts |
| **1. Minimal factory (one ticket at a time)** | A labelled ticket becomes a draft PR while you do other work | launchd job, JQL poller, lock per key, `worktree.sh`, SDK runner with pinned models, caps, sandbox and deny rules. SQLite with 4 tables. FastAPI + HTMX + SSE dashboard with inbox, board and run page. Resume after a stop. Copy-to-post for drafts. No Jira writes | 10 tickets run. You know the success rate, pauses and cost per ticket |
| **2. Fewer interruptions** | Runs continue across waits and work goes on after the PR | 2–3 runs in parallel (one lower-env deploy at a time per environment). `defer` hook for questions. Waiters for Jira answers (compare timestamps, as the refresh does), PR comments and CI, plus a follow-through skill. Approve-then-post through your token. macOS notifications for decisions and failures only. Guard hooks for protected paths and test edits. | **3. Later, only when allowed** | Grow past one laptop | Service accounts and push intake once admins can help. A container or VM runner. ## Decisions still open

| Decision | Options | Lean |
|---|---|---|
| Claude on work repos | Allowed or not, given the company licenses Copilot | Confirm before running it on work code; build and prove it on a non-work repo first |
| Auth | Subscription login or API key | Subscription for phase 0–1 if allowed for personal use; API key if it ever serves others ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)) |
| Opt-in signal | `agent-ready` label, or a Start button on the dashboard | Label if you can add it; button otherwise |
| Factory writes to Jira | None, or labels such as `agent-running` | None in phase 1 |
| Drafted posts | You copy and post, or approve in the inbox and the factory posts | Copy in phase 1, approve-then-post in phase 2 |
| Policy defaults per repo | Push, draft PR, stubs, lower-env deploy | Push and draft PR yes; stubs off (the mock console needs your sign-in); deploy only when the env is free |
| Session shape | One session per ticket, or one per stage | One per ticket, as the skill runs now; change only if phase 1 data says so |
| Later team database | Hosted Supabase (Sydney), self-hosted Supabase, or plain Postgres in the company's AWS | Decide only when a team version is real; hosted Supabase needs a risk review of EU logs and global support access |
| Language | Python SDK + FastAPI, or TypeScript SDK + Hono + React | Python |
| Caps | Per ticket, per day | $20 and 2 hours per ticket, plus a daily ceiling |
| Transcript retention | How long, and where | Local disk outside every repo; a short retention until compliance says otherwise |

## Conclusion

Taking away Copilot and the admin asks makes the factory smaller, not bigger. Claude Code already has the durable parts (resumable sessions, `defer`, budgets, cost per model). Your skill already decides when the work is done. So the factory's own code is a poller, a lock, a runner, four tables and a page. That is roughly what Symphony, Archon and Vibe Kanban each built. The real risk sits elsewhere. An unattended run on your laptop holds your personal keys, so the deny rules, the sandbox and idempotent side effects are where the effort should go.

The evidence also has gaps. Nobody publishes success or intervention rates for a factory like this, and your skill chain has not been run headless yet. The Claude docs do say `SendMessage` works in `-p`: it doesn't need agent teams, it resumes a finished subagent in the background with its full history, and a `-p` run stays open until background subagents finish ([sub-agents](https://code.claude.com/docs/en/sub-agents#resume-subagents), [headless](https://code.claude.com/docs/en/headless#background-tasks-at-exit)). One catch: an idle wait can be cut after 10 minutes by default, so set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`. The answer to "is Claude allowed on work code" sits outside the docs. Phase 0 is cheap and answers the first two. Your own numbers from phase 1 should then decide what to automate next.

## How I would approach it

1. Run `sdlc-ticket` headless by hand once on a small ticket in a non-work repo, with `dontAsk`, an allow list and a $20 cap, and write down every denial or prompt.
2. Add a `factory` mode to `sdlc-ticket`: read a per-repo policy file instead of asking the start round, and write the end report as JSON too.
3. Repeat step 1 until three tickets reach a draft PR with no prompts.
4. Write a small Python program: poll Jira with your token, lock the ticket, make the worktree, run the skill through the Agent SDK, and save the result to SQLite.
5. Add a simple dashboard with the "needs you" queue on top, a board and a run page, plus a Resume button that continues the session with your answer.
6. Add the safety fence: pinned models, budget and time caps, the macOS sandbox, and deny rules for merge, ready, force push and Jira writes.
7. Let it run 10 real tickets, one at a time. Measure success, pauses and cost.
8. Only then add parallel runs, the `defer` hook for questions, waiters for answers and PR comments, and an eval set.
9. Leave service accounts, containers, Postgres and any release step until you can ask the admins and compliance.
