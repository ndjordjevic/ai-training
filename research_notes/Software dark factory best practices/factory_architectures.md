# Software factories / dark factories: architectures and practices (as of Nov 2026)

## 1. What "dark factory" means in software, and the rules its practitioners use

### Takeaway
"Dark factory" is the top rung (Level 5) of Dan Shapiro's Jan 2026 five-level ladder: specs go in, software comes out, no human writes or reviews the code. StrongDM's three-person AI team is the main real example. Their rules: no hand-written code, no human code review, end-to-end "scenarios" held out from the agents in place of agent-written tests, a probabilistic "satisfaction" score in place of green/red, and a "Digital Twin Universe" of cloned third-party services. Critics point out that this moves human judgment upstream into specs and scenarios. It does not remove it.

### Cited Findings
**Dan Shapiro's levels (Jan 2026)**
- Level 0: all manual, "not a character hits the disk without your approval." Level 1: hand discrete tasks (tests, docstrings) to an "AI intern." Level 2: pair with AI "like a colleague." Level 3: "You are the human in the loop." AI writes code and you review diffs, often across several agents. "For many people, this feels like things got worse." Level 4: spec-driven. You write specs and skills, review plans, then "leave for 12 hours, and check to see if the tests pass." Level 5, Dark Factory: "a black box that turns specs into software," done by small teams of fewer than 5 people. — [Dan Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)
- Shapiro's advice: don't stop at Level 2 ("feel like you are done. But you are not done"). Most people top out at Level 3 because the job turns into reviewing diffs. Getting to Level 4 means moving from reviewing code to specifying work and reviewing plans. — [Dan Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)
- Other ladders exist and the numbering differs by author. env.dev uses levels 0–5 (L3 = human diff review, L4 = spec-driven with automated evaluation). Steve Yegge uses an 8-level ladder. Most blog sources place typical professional use around Level 3. — [MindStudio](https://www.mindstudio.ai/blog/agentic-coding-levels-explained), [env.dev](https://env.dev/guides/dark-factory-pattern) (secondary, mostly vendor blogs)

**StrongDM Software Factory (Simon Willison write-up, Feb 2026)**
- Definition: "non-interactive development where specs + scenarios drive agents that write code, run harnesses, and converge without human review." — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- Rules: code "must not be" written by humans and "must not be" reviewed by humans. Mantra: "Why am I doing this?" (meaning the model should be doing it). Practical rule: if you haven't spent "at least $1,000 on tokens today" per human engineer, "your software factory has room for improvement." Willison estimates that at about $20k/month per engineer and questions whether it is sustainable. — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- Team: 3 people (Justin McCarthy, Jay Taylor, Navan Chauhan). Started July 2025 with a "no hand-coded software" rule. Within 3 months they had an agent harness, Digital Twin clones of about 6 services, and simulated test swarms. — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Scenarios in place of tests:** end-to-end user stories, "often stored outside the codebase (similar to a 'holdout' set in model training)," validated flexibly by an LLM. The reason: if agents write both the code and the tests, they can game the tests (e.g. assert true). — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Satisfaction metric:** replaces "suite is green" with "what fraction of [trajectories] likely satisfy the user?" — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Digital Twin Universe (DTU):** behavioral clones of Okta, Jira, Slack, Google Docs/Drive/Sheets, built by agents from public API docs as self-contained Go binaries. They allow thousands of scenarios per hour with no rate limits, API costs or danger to live systems. Jay Taylor's tip: use popular public SDK client libraries as the compatibility target, aiming for "100% compatibility." — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Released artifacts:** Attractor (github.com/strongdm/attractor), the non-interactive coding agent, ships as 3 markdown spec files with no code: "feed the specs to your own agent." cxdb is an "AI Context Store" that keeps conversation histories and tool outputs in an immutable DAG (~16k lines of Rust, 9.5k of Go, 6.7k of TS). — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Named techniques** (factory.strongdm.ai/techniques): Gene Transfusion (reuse patterns from existing systems), Semports (porting code between languages), Pyramid Summaries (layered summaries agents can zoom into). — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- **Concrete failure:** StrongDM's agents wrote `return true`, which passes tests while doing nothing. This is the origin of holdout scenarios. — [Stanford Law CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/)
- **Criticism:** human involvement is "relocated upstream from code review to scenario design," not removed. "Who verifies the verifiers?" Applying no-review to security software is risky. — [Stanford Law CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/), [Pragmatic CTO via HN reader](https://hn.jakechampion.name/reader/https://www.thepragmaticcto.com/p/the-software-factory-when-no-human). Willison calls verification "the most consequential question" and also flags cost and business-model risk (competitors can clone features in hours). — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/)
- A practitioner's personal "dark factory" experiment concludes: "Dark Factory isn't 'no humans'. It's 'humans move up the stack'," and recommends carving out bounded areas rather than going fully dark. — [Johnny Butler](https://world.hey.com/johnnybutler/dark-factory-no-humans-should-write-code-and-what-it-taught-me-3f1a06f0)

### Inferences
- The parts a small team can actually adopt are the cheap ones: holdout scenarios kept outside the agent's repo or context, fakes/twins of external APIs, and a judged "satisfaction" check. The $1k/day spend and the no-review rule are not required to get those benefits.
- In a regulated fintech setting (Basiq/Cuscal), Level 4 (spec-driven with human plan review and human merge) is the realistic target. Level 5 is better used as a design direction than as a policy.

## 2. Reference implementations and their pipelines (intake → plan → implement → verify → review → merge)

### Takeaway
The best-documented open design is OpenAI's Symphony SPEC: a tracker-polling orchestrator with one workspace per issue, a hot-reloaded WORKFLOW.md, retries with exponential backoff, stall detection, and a "Human Review" handoff state. Anthropic's long-running harness supplies the pattern inside each run: an initializer agent, then a coding agent working one feature at a time, with a JSON feature list, a progress file, git and browser testing. GitHub Copilot coding agent is the turnkey version available to the company. It takes issues from GitHub/Jira/Slack/Teams, runs in a cloud or Actions sandbox (59-min cap on Actions), opens one PR per task, and leaves merging to humans.

### Cited Findings
**OpenAI Symphony (github.com/openai/symphony, "low-key engineering preview for trusted environments")**
- Purpose: let teams "manage work instead of supervising coding agents." It watches a Linear board, spawns an agent per task, and the agents supply "proof of work: CI status, PR review feedback, complexity analysis, walkthrough videos." When a human accepts, "the agents land the PR safely." It "works best in codebases that have adopted harness engineering." Ships as SPEC.md (build it in any language) plus an experimental Elixir reference implementation. — [openai/symphony](https://github.com/openai/symphony)
- Components: Workflow Loader, Config Layer, Issue Tracker Adapter, Orchestrator (single in-memory state, poll tick), Workspace Manager, Agent Runner (launches `codex app-server`), optional status HTTP server. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- WORKFLOW.md: YAML front matter plus a Markdown prompt body, hot-reloaded (an invalid reload keeps the last good config). Keys and defaults: `polling.interval_ms` 30000, `agent.max_concurrent_agents` 10, `agent.max_turns` 20, `agent.max_retry_backoff_ms` 300000, `agent.max_concurrent_agents_by_state`, `codex.turn_timeout_ms` 3600000, `codex.stall_timeout_ms` 300000, `hooks.after_create|before_run|after_run|before_remove` (timeout 60 s), `tracker.required_labels`, `active_states`, `terminal_states`. The prompt template is strict (unknown variables fail the run) and gets `issue` and `attempt`. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Claim states: Unclaimed → Claimed → Running → RetryQueued → Released. Run phases: PreparingWorkspace → BuildingPrompt → LaunchingAgentProcess → InitializingSession → StreamingTurn → Finishing → Succeeded / Failed / TimedOut / Stalled / CanceledByReconciliation. Teams typically use a non-terminal handoff state such as "Human Review," so a successful run does not auto-close the issue. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Dispatch: an issue must be in an active state, have all required labels, not be already claimed, and have free global and per-state slots. Sort order: priority, then oldest created, then identifier. After each turn the worker re-fetches the issue and continues only if it is still active. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Workspaces: `<root>/<sanitized identifier>`, reused across runs and kept after success. The agent's cwd must be the workspace, and the workspace must stay under the root. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- The tracker is the control plane. Moving an issue to a terminal state stops the run and deletes its workspace. Moving it to a non-active state stops the run and keeps the workspace. A restart rebuilds state from the tracker and the filesystem. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)

**OpenAI harness engineering (Ryan Lopopolo, Feb 11 2026)**
- A 5-month internal beta of about 1M lines (app, infra, tooling, docs) with no manually written source code, steered by "a small team of engineers." Engineers "designed environments, specified intent, and gave structured feedback." A structured docs/ directory (maps, execution plans, design specs) is the agents' system of record, and linters and CI check the cross-linked docs. A layered dependency order (Types → Config → Repo → Service → Runtime → UI) is enforced by mechanical rules and structural tests. Agents use logs, metrics and spans in isolated dev environments to reproduce bugs. — [InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)
- Secondary sources say it was a 3-engineer team, "thousands of PRs," and no human review before merge. — [ZenML LLMOps DB](https://zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code), [Latent Space](https://latent.space/p/harness-eng) (not verified against the original: openai.com returned 403)

**Anthropic, "Effective harnesses for long-running agents" (Nov 26 2025, older but still the reference)**
- Two prompts on the same harness. An **initializer agent** writes `init.sh`, a progress log, an initial git commit and a **JSON feature list** (200+ features for a claude.ai clone, all marked failing). A **coding agent** runs every later session: read the progress file and git log, run init.sh and a basic e2e smoke test, pick **one** feature, implement it, verify it, mark `passes` true, then commit and update progress. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Agents may change only the `passes` field: "It is unacceptable to remove or edit tests." JSON was chosen because models are less likely to rewrite it than Markdown. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Verification: unit tests and curl missed e2e bugs. Telling Claude to use Puppeteer MCP and "do all testing as a human user would" helped a lot. Limitation: browser-native alert modals are invisible to it. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Observed failure modes: trying to one-shot the app, declaring the whole project done early, marking features passing too early, leaving undocumented half-work, and wasting time working out how to run the app. Each one maps to a fix (feature list, one feature at a time, self-verify, notes plus git, init.sh). — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**GitHub Copilot coding agent (company runtime)**
- Researches, plans and implements in the background, and runs tests and linters in a cloud environment. Entry points: the Agents tab/panel, issues, PRs, the dashboard, VS Code, Copilot CLI, the Copilot app, Mobile, Slack and Teams. Automations can run "on a schedule or in response to repository events." Code-scanning alerts can be assigned to it. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- Environments: cloud sandbox (honors repo and org firewall allowlists, can span repos in one org, supports a dotfiles repo for personal instructions, skills and custom agents), GitHub Actions (custom compute, self-hosted runners, single repo, **hard 59-minute limit per session**), or remote. One branch and one PR per task. Rulesets or branch protection can block it unless an admin grants a bypass. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- Gating features: Copilot code review (on request or automatic). **Agent Merge / "Watch and fix"** watches a PR and works on chosen blockers such as failed workflows or merge conflicts. **Hooks** "run commands during agent work for validation or logging." **Custom agents and agent skills** give task-specific instructions. GitHub warns that session logs "do not replace your own review and testing." — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- **Jira:** public preview Mar 5–6 2026. Assign a Jira issue to Copilot or @mention it. It reads the description and comments, opens a draft PR and posts updates to Jira. Requires Jira Cloud with Rovo. — [GitHub changelog](https://github.blog/changelog/2026-03-05-github-copilot-coding-agent-for-jira-is-now-in-public-preview/). Mar 25: model choice from Jira, the Jira key in the PR title and branch, Confluence via the Atlassian MCP server. — [GitHub changelog](https://github.blog/changelog/2026-03-25-github-copilot-for-jira-public-preview-enhancements/). **GA Jun 24–25 2026**: real-time progress in Jira, custom agents, custom fields, review requests, and follow-ups from the Jira chat panel that continue on the same PR. — [GitHub changelog](https://github.blog/changelog/2026-06-24-github-copilot-for-jira-is-now-generally-available/)

**Ralph Wiggum loop (Geoffrey Huntley, mid-2025)**
- The purest form is `while :; do cat PROMPT.md | claude ; done`. Each pass starts with fresh context, and memory lives only in the filesystem and git. "The prompt never changes; the codebase does." It relies on external checks (tests, builds, explicit completion markers) rather than the agent's own judgment. Philosophy: "better to fail predictably than succeed unpredictably." It needs a sandbox (Docker/E2B/Modal) because it runs with permissions skipped. Anthropic's Claude Code plugin version uses a Stop hook in a single session, so context accumulates instead. — [FutureAGI](https://futureagi.com/blog/loop-engineering/ralph-loop/), [Tessl](https://tessl.io/blog/unpacking-the-unpossible-logic-of-ralph-wiggumstyle-ai-coding), [second-brain notes](https://second-brain-nuxt.vercel.app/ralph-wiggum-loop-from-first-principles) (secondary; the "$50k contract for $297" and months-long language-building claims are unverified)

**Parallel-agent orchestrators (local, human-driven Level 3 tools)**
- Conductor (Mac app), Claude Squad (tmux plus git worktrees in a TUI), Crystal and Vibe Kanban (agent-neutral kanban board) each give every agent its own worktree and branch. Sculptor isolates agents in containers instead (research preview). Worktrees share the host machine, so a runaway install or migration can still hit real files, which is why containers are pitched as safer. Vibe Kanban's company bloop shut down on Apr 10 2026, and the project continues as community-maintained Apache-2.0. — [Nimbalyst](https://nimbalyst-website.pages.dev/blog/best-git-worktree-tools-ai-coding-2026/), [AgentsRoom](https://agentsroom.dev/blog/best-multi-agent-coding-tools) (vendor comparison blogs; treat rankings with caution)
- Curated list of factory projects: [awesome-software-factories](https://github.com/varun1505/awesome-software-factories)

### Inferences
- Symphony's SPEC fits the user's setup well even without Codex. The parts that matter are runtime-neutral: the tracker as the control plane, a Human Review handoff state, one workspace per issue, per-state concurrency caps, backoff, a stall timeout and lifecycle hooks. `codex app-server` could be swapped for `claude -p` (personal) or `copilot` CLI non-interactive mode (company), but that would need checking.
- For the company runtime, Copilot coding agent plus the Jira GA integration plus Agent Merge "Watch and fix" already covers intake → PR → CI-fix with no custom infrastructure. The custom work is in specs, custom agents/skills, hooks, and copilot-setup/firewall config. The 59-minute Actions cap means tasks must be cut small (which matches Anthropic's one-feature-per-session advice), or the cloud sandbox should be used.

## 3. Pipeline stages, state machines, gating, "done" criteria, retries and escalation

### Takeaway
Across implementations, "done" is decided outside the agent: a tracker state set by a human (Symphony's Human Review), a JSON feature list that agents may only flip to passing after browser testing (Anthropic), holdout scenarios scored by an LLM judge (StrongDM), or CI plus review gates on the PR (Copilot). Stuck agents are handled with timeouts plus retry with backoff (Symphony), fresh-context restarts (Ralph), and handing back to humans through tracker comments.

### Cited Findings
- Symphony retries: a normal exit schedules a continuation check after 1 s. An abnormal exit uses `min(10s × 2^(attempt−1), 5 min)` backoff. On retry, the issue is re-fetched and the run released if it is gone or terminal, requeued if no slot is free. Stall = no Codex event for `stall_timeout_ms` (5 min), which kills the worker and queues a retry. `turn_timeout_ms` is a silence limit, not a total runtime cap. `max_turns` 20 per worker. Reconciliation runs every tick before dispatch. — [Symphony SPEC](https://raw.githubusercontent.com/openai/symphony/main/SPEC.md)
- Anthropic: verify the basic app works before starting new work, and mark a feature passing only after e2e testing. Git lets the agent revert to a known-good state. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Plan gate before code: Overnight's first run posts an implementation plan to the Linear issue. A human replies with changes or "go," and only then does a second run in a fresh sandbox implement it and open a PR. — [Emre Sarbak / Overnight](https://dev.to/emresarbak/overnight-turn-linear-issues-into-pull-requests-3cnp)
- Opt-in gate: Pierson Marks's factory starts work only when an `auto` label is added. Agent-created issues do not get the label by default, so a human chooses what gets built. The agent sets the issue to In Progress, skips issues already in progress or done, and prefixes its comments with `[Claude]`. — [Pierson Marks](https://www.piersonmarks.com/posts/building-a-software-factory)
- Review-agent pitfall: one build log found its automated reviewer approved a diff when it could see only 6% of it, could not run tests and had no design doc. "A human reviewer wouldn't accept" that. — search snippet of [Aitherium blog](https://aitherium.com/blog/dark-factory-first-run-what-broke-what-worked-whats-next) (not fetched; snippet only)
- Copilot: one PR per task, branch protection and rulesets apply, and Agent Merge works on CI failures and conflicts the user selects. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)

### Inferences
- A practical state machine for a Jira/Linear-driven personal factory: `Ready (label: auto)` → `Planning` → `Plan Review (human)` → `In Progress` → `Verifying` (CI + browser/e2e + holdout scenarios) → `Human Review` → `Done`. On repeated failure or a stall, go to `Blocked/Needs Human` with the agent's notes attached as a comment.
- An AI reviewer should get the full diff, the ability to run tests, and the spec. Otherwise it gives false confidence.

### Gaps
- No source gave measured retry, success or escalation rates for any factory.

## 4. Phased adoption path and what went wrong

### Takeaway
Practitioners agree: start with one loop, keep the existing tracker as the queue, put a human gate on intake (label) and on plans, move verification out of the agent's control, and only then cut back human review. Common failures are tests that agents game, premature "done," review agents with too little context, unsandboxed runs, and cost.

### Cited Findings
- "Start small with a single loop, try it out, refine it, then add more." Split the system into "create work → store work → complete work." Tools that force workflow changes "will fade into irrelevance." Even pre-triage alone (agents filing good issues) gives leverage. — [Pierson Marks](https://www.piersonmarks.com/posts/building-a-software-factory)
- Shapiro's ladder doubles as the adoption path: L2 pairing → L3 reviewing parallel agents (feels worse) → L4 specs, skills and plan review, then leave it running → L5 only for tiny teams. — [Dan Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)
- Symphony "works best in codebases that have adopted harness engineering" (docs as system of record, mechanically enforced architecture). In other words, prepare the repo before automating intake. — [openai/symphony](https://github.com/openai/symphony), [InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)
- Failures: `return true` test gaming (StrongDM) — [Stanford Law CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/). Premature victory and one-shotting — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). Unsandboxed skip-permissions loops — [FutureAGI](https://futureagi.com/blog/loop-engineering/ralph-loop/). Worktrees not isolating side effects — [Nimbalyst](https://nimbalyst-website.pages.dev/blog/best-git-worktree-tools-ai-coding-2026/). Cost at around $20k/month per engineer — [Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/). Overnight won't open-source "until … it won't eat anyone's codebase" — [Overnight](https://dev.to/emresarbak/overnight-turn-linear-issues-into-pull-requests-3cnp)

### Inferences
- Suggested phases for the user: (1) Copilot coding agent from Jira on small, well-specified tickets, with a human merge. (2) Add custom agents/skills, hooks and a plan-approval step. (3) Add holdout scenario checks and service fakes in CI that the agent cannot edit. (4) Use Agent Merge "Watch and fix" for CI and conflicts. (5) Only for low-risk repos, consider auto-merge on green scenarios.

### Gaps
- No rigorous before/after productivity or defect data from any factory adopter was found.

## 5. Practitioner case studies (personal factories on Jira/Linear/GitHub Issues)

### Takeaway
Real personal factories are small glue: tracker label → webhook → hosted agent session (Claude Code cloud routines, Modal sandbox) → skill that runs the SDLC → PR. Scheduled agents feed the queue from telemetry.

### Cited Findings
- **Pierson Marks (Jul 9 2026), all on a Claude subscription:** a Linear `auto` label triggers a webhook to a small Hono service, which POSTs to Anthropic's routine trigger API. A Claude Code cloud routine fetches only that issue and runs a `/do` skill (fetch context → implement → verify in browser with Playwright/Agent Browser → open PR → watch comments). Pre-triage routines file Linear issues: a daily 5am health check (PostHog, Vercel), a weekly UX/feedback scan (Intercom, PostHog replays), and a daily 6am churn analysis (Stripe, Supabase) that posts to Slack. Shared MCP connectors work in both local and cloud sessions. He chose this over a VPS or Mac mini. Browser verification is "hopefully," not guaranteed. The post does not cover merge policy or costs. — [Pierson Marks](https://www.piersonmarks.com/posts/building-a-software-factory)
- **Overnight (Emre Sarbak / Emotion Machine):** a Linear label fires a webhook straight to Modal endpoints, with no backend to maintain. A disposable Modal sandbox uses a cached repo clone volume synced with main. Codex or Claude Code posts a plan to Linear, a human approves, and a fresh sandbox implements and opens the PR. The target is 10–20 agent sessions per person per day, and runs can be started from mobile. — [Overnight](https://dev.to/emresarbak/overnight-turn-linear-issues-into-pull-requests-3cnp)
- **Cyrus:** a Linear integration where the Claude Code agent is assignable like a teammate. — [Cyrus](https://www.atcyrus.com/stories/linear-claude-code-integration-guide) (vendor, not fetched)
- Other guides: [freeCodeCamp: software factory with Claude Code](https://www.freecodecamp.org/news/how-to-build-software-factory-with-claude-code/), [Patrick Ellis: four-pillar orchestration layer](https://patrickellis.io/articles/turn-claude-code-into-a-software-factory) (not fetched)

### Inferences
- Runtime fit. **Claude Code (personal):** cloud routines plus a webhook, a Ralph-style loop, or a Symphony-like runner around `claude -p`, with skills holding the SDLC steps. **Copilot (company):** Jira or GitHub issue assignment to Copilot coding agent, custom agents/skills/hooks, Agent Merge, and repo automations on schedules or events. That covers the same intake → PR flow with no custom webhook service. A Symphony-style runner around Copilot CLI would only be needed for local or multi-step control.

### Gaps
- No Jira-driven (as opposed to Linear-driven) personal-factory write-up was found, apart from the official Copilot-for-Jira integration.
